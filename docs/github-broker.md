# GitHub metadata through the main broker

**Status: fixed synthetic integration. No live GitHub access or real key input.**

The main broker now authorizes the versioned `synthetic.github.repository-metadata.v1` operation. Its existing issue-status interface remains compatible. GitHub uses the same principal/session, canonical review, request lifecycle, budget, deduplication, expiry and revocation engine, with a private synthetic adapter and a mandatory new intent journal.

```sh
cargo run --locked --offline --example github_broker_spike -- /canonical/test-parent/new-journal
```

This example demonstrates a trusted embedding host inspecting and approving a fixed request, obtaining safe metadata, replaying its result and explicitly revoking the mock token. It is not proof of human presence. All App/account/repository identifiers are fictional fixtures; the account label is fixed to the intended personal owner. No credentials are accepted or generated by a real provider.

## One authority engine, explicit compatibility

- Legacy `PrepareInput`, `RunView`, `ApprovalView`, `Control::synthetic`, issue-status methods, wire version 1 and default MCP adapter retain their shapes and behavior.
- Typed `OperationProfile`, `OperationIntent`, `OperationResult`, `OperationPrepareInput`, `OperationRunView` and `OperationApprovalView` represent the versioned path. Operation and result kinds are checked; an issue-status result cannot stand in for GitHub metadata.
- `Control::synthetic_github` accepts only the exact fixed GitHub fixture profile, per-request reviewed approval, one concurrent dispatch and at most 32 uses/retained requests. Caller-provided provider executors, real key references and live configuration are unavailable.
- Legacy handle methods reject GitHub handles before mutation or dispatch. Unchecked legacy `approve` and bounded-session autoapproval cannot authorize GitHub. The trusted control must use `inspect_operation_approval` followed by `approve_operation_reviewed` with the exact returned view.
- Agent-facing version 2 exposes discovery, prepare, request approval, invoke, status and cancel. It has no approval, provider-revocation, credential, setup or arbitrary execution method.

The resolved review includes broker epoch, principal/session, prepared handle and caller request ID, full profile/enrollment/signer/result bindings, operation parameters, policy generation, expiry, complete grant/session/request limits and remaining budget. Its human-channel representation is non-secret metadata. The broker compares the complete view under its policy lock. A changed account, repository, key version, operation kind, output contract, handle, broker instance, request ID, budget or generation does not inherit the old review.

There is no second source of consent in the adapter. The core creates a private non-serializable dispatch receipt only after approval checks. The adapter's standalone simulated-approval method is disabled for a broker-owned instance. The original no-input mock demos remain separate test fixtures and cannot operate the broker-owned adapter.

## Reservation, effects and uncertainty

The broker's lock orders approval/current-binding checks, use consumption, adapter reservation, the synced journal reservation and future-use revocation. No provider call runs under that lock. The adapter produces opaque, non-Clone reserved work and consumes it once outside the policy lock. Lock ordering is core, then fixture, then journal; the fixture/provider never reacquires core authority.

A failed or uncertain journal reservation consumes the core use once, returns retained uncertainty and blocks fresh request IDs. A known pre-provider persistence failure can instead be a terminal `persistence_unavailable`; it still consumes its reservation and blocks further work. A post-effect/terminal persistence failure remains `outcome_unknown`. The tested handled fault paths do not refund a use, silently retry or leave a run reported as dispatched. Poisoned locks or host aborts can instead make the broker unavailable; restart inspection still restores no authority.

Ordinary result lookup/replay requires the existing valid session. GitHub has one narrow exception: the closed `outcome_unknown` receipt remains available to that same bound client/handle after expiry, clock regression or stop. It contains no result data and permits no new effect, approval or session refresh. Legacy issue-status behavior is unchanged.

`Control::revoke` stops new reservations and persists local future-use revocation for GitHub. A previously reserved operation may complete. `Control::revoke_provider_tokens` is a separate explicit trusted-control mock effect; it is absent from the agent wire. Local grant revocation alone never claims that GitHub revoked a token. Revocation uncertainty remains explicit.

The core and adapter use the same elapsed-clock origin. The adapter maps it to a fixed synthetic UTC anchor for JWT/token fixtures; this is not a live UTC implementation. Core idle/max/request checks remain authoritative. Independent human authentication and host lifecycle enforcement remain open gates.

## Journal schema 2

Standalone journal schema 1 remains inspectable. Broker-owned journals use schema 2 and the exact hyphenated broker operation ID. Schema 1 retains its historical underscore adapter ID; neither schema can be mixed into the other's file.

The schema-2 header pins the actual core principal/session, initial budget, profile/policy generation, session start, idle/max/request limits, request/concurrency bounds and reviewed-request mode. Each reservation records the exact fixed enrollment, caller ID/epoch, prepared handle, reviewed profile/key/adapter/output versions, review deadline and the budget displayed at approval separately from budget before/after consumption. Another already-approved request may legitimately consume a use between approval and this dispatch.

Inspection verifies fixed schema/context, unique request and prepared IDs, exact profile/enrollment/review binding, contiguous sequence and budget progression, applicable max-session/request windows and valid effect transitions. The idle limit is recorded as context; the journal lacks success timestamps needed to independently reconstruct every historical idle decision. More generally, the stored claims are not authenticated proof of a human decision or authorized writer.

Recovery remains inspection-only with zero restored grants/sessions and no automatic retry/refund. Unknown mints/reads/revocations and issued-but-unrevoked tokens require reconciliation. Complete valid rollback/replacement cannot be detected under the [trusted-storage assumption](github-intent-journal.md#strict-decoding-and-its-limits). No token/JWT bytes enter schema 2.

## Wire version 2

A preparation request names an explicit operation kind:

```json
{"version":2,"action":{"method":"prepare_operation","params":{"request_id":"github-1","profile_id":"github-metadata","operation":{"kind":"synthetic.github.repository-metadata.v1","parameters":{"repository_id":4242}}}}}
```

Request approval, then pause for the separate control decision:

```json
{"version":2,"action":{"method":"request_approval","params":{"prepared_request_id":1}}}
{"version":2,"action":{"method":"invoke_approved","params":{"prepared_request_id":1}}}
```

The result uses an explicit kind and a three-field projection:

```json
{"version":2,"result":{"prepared_request_id":1,"state":"succeeded","result":{"kind":"synthetic.github.repository-metadata.v1","value":{"repository_id":4242,"private":false,"archived":false}},"error":null},"error":null}
```

Version-2 discovery uses `{"version":2,"action":{"method":"discover_operations","params":{}}}`. Unsupported versions, unknown fields, duplicate members, forged approval and mixed parameter/result kinds are rejected. A typed preliminary version parser selects the full typed decoder without converting raw requests into a duplicate-collapsing JSON value. Existing frame/connection bounds and mandatory LF remain unchanged.

The explicit `mcp::Adapter::new_v2` / `mcp::serve_v2` mapping still uses MCP `2025-11-25` and the same six tool names, with versioned operation inputs. The original constructor/default CLI stays version 1. Host/client labels never establish principal or approval. The socket bridge checks the response against the requested broker version while retaining its epoch check; the transport greeting remains version 1.

## Foreground wiring and verification limit

The new commands are implemented and compiled:

```sh
aegis synthetic-github-broker --socket-dir /canonical/test-parent/new-socket --journal-dir /canonical/test-parent/new-journal
aegis mcp-v2 --socket /canonical/test-parent/new-socket/agent.sock
```

Use the broker terminal's `inspect ID`, `approve ID`, `cancel ID`, `revoke`, `revoke-tokens` or `stop`. Nonterminal control is refused unless the explicit `--synthetic-control-pipe` test flag is supplied. That flag is not human authentication.

On the current Linux cloud host, Unix listener binding is denied with `EPERM`. Existing 14 listener-dependent interface tests therefore remain unsuccessful; the new foreground/socket path is compiled but not claimed as end-to-end verified here. In-process V2 JSON/MCP tests, core authorization/ledger tests, the headless-refusal subprocess check and the standalone broker example provide the narrower evidence. See [verification](verification.md).

## Remaining real-use gates

Synthetic policy integration is complete for this operation. Live availability remains false. Protected key custody and maintained RS256 signing, independently authenticated human approval, tested OS separation, authenticated/rollback-aware operational storage and reconciliation, bounded live transport/enrollment checks and an isolated Git recipient or separately reviewed writes remain required. No org access, Workflows/admin permissions, user tokens, services, security configuration, key provisioning or publication was added.

## Optional disposable signing

The separate [approval-bound signing composition](github-signed-composition.md) adds `Control::synthetic_github_signed` only with `signing-spike`. It keeps this fixed provider/operation policy and schema 2, resolves a private one-shot permit only after durable reservation and verifies the resulting opaque JWT in the mock exchange. `Control::synthetic_github`, foreground commands and MCP selection remain mock-only. This does not enable real key input or live readiness.
