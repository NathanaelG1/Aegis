# Integrated synthetic vault-to-recipient path

**Optional test milestone, not a usable real-key vault.** `vault-spike` composes the existing main broker with signed principal/approval assertions, an exact ACL, age-encrypted fixed secret records, a private encrypted recipient capsule, signed acknowledgements and durable synthetic history. It accepts only built-in canaries. No live import, HTTP listener, protected human entry, independently protected generation anchor, actual isolated application or host-containment guarantee is implemented. `require_live_deployment()` always returns `unsupported_deployment`.

```sh
parent="$(mktemp -d /tmp/aegis-vault-demo.XXXXXX)"
cargo run --locked --offline --features vault-spike --example vault_spike -- \
  create "$parent/vault" "$parent/fixture-kit" "$parent/recipient"
cargo run --locked --offline --features vault-spike --example vault_spike -- \
  inspect "$parent/vault" "$parent/fixture-kit" "$parent/recipient"
```

Every destination for `create` must be new. The separate fixture kit contains disposable age/RSA private keys for this exercise, including both simulated actors; it grants no service access. It is not protected custody and must never contain a real key. The demonstration automatically signs its test approvals, which establishes signature-verification behavior, not a human action. Output is a closed status/count report with human-presence, protected-deployment and real-key readiness explicitly false. `inspect` restores no session or grant.

## One integrated authority path

The subsequent [role-separated protocol increment](vault-protocol.md) provides reusable bounded agent/admin connection handlers. Runtime storage and recipient objects now retain only their role-specific key material, and authentication gates retain public actor verifiers. The fixture loader and automatic demonstration still have all-role dummy material; this is not protected provisioning.

The optional `Delivery` operation variant uses the main broker's existing prepare/review/reservation/revoke/idempotency machinery. Its typed proposal contains only exact secret ID/version, recipient ID/enrollment/configuration revision/slot, repository scope and expected installed generation. The profile and signed manifest constrain these to two fixed canary versions. No arbitrary file path, provider URL, authentication header, command, recipient key or credential value is accepted from the agent.

The authentication fixture enrolls different RSA public verifiers for the agent and human-control actor. Maintained `jsonwebtoken`/AWS-LC verifies RS256 assertions with strict bounded JOSE/claim parsing. Claims bind issuer/subject, distinct role audience and purpose, broker epoch, enrollment/ACL revision, a server-generated one-use challenge, exact review/dispatch digest and a 30-second validity interval. Unknown/wrong keys, role/audience/algorithm changes, duplicate/unknown claims, stale epochs and replay fail. This is an application-specific signed-assertion experiment, not an OAuth server, WebAuthn implementation or human-presence attestation. The clock is still the injected synthetic origin, not production UTC.

Successful connection returns an opaque, non-serializable authenticated-session capability. It binds a specific `AgentClient`; earlier unauthenticated handles and another broker's capability cannot inherit it. Stateful/versioned agent methods and legacy handle wrappers check that capability under the broker lock. The old legacy discovery function remains an unverified static public issue-status catalog; it discloses no vault policy or authority. The fixture supports one enrolled agent principal/session, not a deployed multi-principal service.

An authenticated principal still needs an exact ACL entry. Empty policy or another profile/version grants nothing. Entries match the whole principal/profile/secret/recipient/resource/contract tuple; partial matches cannot be combined. Existing tighter request/session/concurrency/use limits remain in force. The fixed persistent budget starts at four uses across cold starts.

Human-control proof is verified inside `approve_inner`, after the canonical view comparison and before approval state changes. A bare `Control::approve_operation_reviewed` therefore cannot approve this operation without the separately signed assertion. The agent's per-invocation proof and ACL are checked before budget decrement, inside the same core lock as revoke. The adapter then syncs its durable reservation before reading/decrypting a secret or handing off a capsule. No agent-provided approval boolean or directory mode selects a protected mode.

## Storage, recipient and durable state

The fixture uses the existing optional age 0.11.1 X25519 implementation for each immutable canary record and for the recipient capsule. A signed manifest binds ciphertext digests, references, ACL entries and the enrolled recipient key. SHA-256 digests are identifiers/integrity comparisons within authenticated records; they are not called tamper-proof provenance.

The private recipient verifies the broker's signature and exact capsule context, decrypts the age payload, checks its reference/content digest and fixed canary value, and serializes expected-generation installation. Its durable accepted record retains encrypted content and a signed acknowledgement. The broker accepts only the matching recipient signature and exact delivery ID/slot/version/generation/capsule binding. The agent sees a bounded projection, never plaintext, raw capsule or raw acknowledgement. This recipient is a same-process fixture, not OS-isolated application delivery or a credential-store adapter.

The journal contains bounded RSA-signed JWS records with schema, vault identity, sequence and previous-record digest. It records verified approval metadata, consumed reservations, handoff intent, terminal acknowledgement/uncertainty and revocation. Historical approval receipts record the broker's verified decision; they do not recreate a human session or serve as new approval. Records are synced before effects, and a separate signed sequence/head anchor is updated before an append is acknowledged. Partial writes, invalid signatures/transitions, missing anchors and an old journal with a newer anchor fail closed. Uncertain writes poison the running writer.

Reservation and revocation also sync an exact signed guard before the core records the attempted transition. A guard is removed only after the corresponding journal record and anchor are durable. A surviving, incomplete or unexpected guard blocks cold start and inspection; there is no automatic repair or refund. This covers a reservation/revocation failure before the first journal byte, which would otherwise leave only the earlier approval on disk. Failure to establish the guard is a pre-transition denial. The guard shares the same trusted-storage assumptions as the journal, so coherent deletion/rollback of all state is still outside the fixture guarantee.

**The fixture anchor is an interface assumption, not independent rollback protection.** An attacker who controls both the vault and fixture kit can read keys and roll back or rewrite both. A production adapter needs an independently protected trust root and generation anchor outside the rollback domain, plus protected writer/recipient namespaces. The current files use new destinations, restrictive creation modes, non-following leaf opens, regular-file/owner/link checks, cooperative locks and syncs. Ancestor checks are not atomic directory-handle traversal. Same-UID/administrator access remains outside the claimed boundary; file modes cannot fix it.

On a valid cold start, signatures, history, anchor and recipient generation are checked; remaining uses/revocation/history survive, but sessions, challenges and executable approvals do not. Fresh authentication and a fresh exact human-control assertion are required. A completed request ID cannot produce another effect under a new session. Missing/corrupt/inconsistent state or an incomplete/unknown handoff prevents a new delivery. No automatic retry/refund or operational repair command exists.

Inspection cross-checks exact recipient delivery IDs and capsule digests against the journal. A missing receipt for a completed operation is inconsistent; an installed receipt for an incomplete/unknown handoff remains inspectable uncertainty. An open recipient revalidates its named file, signed history and current state before acknowledging another install. Tested truncation, corruption or replacement latches failure and retains unknown outcome rather than reporting a successful rotation. These checks do not make directory traversal or hostile namespace mutation atomic.

Rotation in this demonstration means installing canary version two with expected recipient generation one. It does not create/revoke a provider credential. Broker revocation blocks future reservations across restart; it cannot erase the recipient's existing canary or invalidate downstream authority. Production provider rotation/revocation and protected recipient cleanup remain separate work.

## Evidence and limits

The focused suite exercises complete delivery/rotation/restart, actual signature verification, role/context/replay/expiry denial, authenticated-handle binding, empty ACL denial, unsigned legacy approval refusal, strict wire rejection, durable budget exhaustion, invalid ciphertext/state/anchor, duplicate in-flight use, expiry during accepted work, failure/panic/bad acknowledgement and subprocess exits around approval/reservation/handoff/completion/revocation. Visibility doctests keep principal/session, host, key and plaintext implementation types private. Full command results belong in [verification](verification.md); a canary-free tested transcript is not proof that all possible agent tools can never obtain a secret.

The feature combines `storage-spike` and `signing-spike`; it introduces no new package or default dependency. Existing native-compiler, passive JWT upstream maintenance, process-global provider and limited zeroization caveats remain. First-party unsafe code is forbidden; this does not audit native/unsafe dependency code. Selected owned secret buffers zeroize on drop, but parser/allocator/native copies, swap, dumps and VM snapshots are not proven erased.

The baseline private Sprite test host can run all Unix interface tests; current agent administrative/exec/filesystem/restore access still invalidates real-key custody there. The [operator-owned ceremony](operator-owned-deployment.md) must be completed only after the missing production code/adapters are reviewed. Removing admin access alone does not turn this canary-only module into an operational secret-entry product.
